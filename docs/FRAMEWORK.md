## 1. 已确认的产品要求

| 项目 | 决策 |
|---|---|
| 交付形态 | 独立仓库、DeepSeek Harness 外部插件，面向个人独立使用 |
| 第一场景 | 前端页面设计与用户偏好适配；B 代码仓库分析、D 日志分析、C 测试与故障定位后续扩展 |
| 可修改对象 | 用户授权的 Skill，包括 SKILL.md、参考资料、Python/Shell 等脚本 |
| 发现机会 | 本地规则观察日常任务并主动提示；用户点击后才调用模型分析 |
| 偏好直接修改 | 同卡确认偏好、修改范围和预算，随后独立调用模型生成候选，不要求先出现观察信号 |
| 偏好澄清 | 轻量主动，每批最多 3 问、每个优化任务最多主动 2 批；支持跳过与关闭，不重复询问有效答案；模型追问计入已确认预算 |
| 偏好作用域 | 本次明确要求优先；默认持久保存到项目，个人默认须明确选择；运行中的优化绑定偏好快照 |
| 优化方向 | 用户明确给出的偏好可作为本次方向；方向不明确时提供建议与取舍供选择，包括能力提升、成本降低和简洁表达等偏好适配 |
| 修改授权 | 每个优化任务授权一次，绑定 Skill、范围、方向和上限；范围内可多轮修改 |
| 启用权限 | 评估后由用户单独确认；迭代过程不自动启用 |
| 本次页面衔接 | 先等待候选检查和用户启用确认，再用新版开始本次页面；首次使用前完成固定版本绑定 |
| 旧会话衔接 | 已用过旧 Skill 时自动创建关联新会话，带入本次需求和确认偏好，保留旧会话及其版本 |
| 候选未采用 | 生成/检查失败、预算耗尽或拒绝新版时保留旧版，由用户选择“用旧版继续”或“停止本次任务”，不自动回退 |
| 原始文件 | 默认保留；覆盖原 Skill 必须有明确、单独的用户同意 |
| 评测来源 | 前端采用固定页面需求与检查、用户明确偏好反馈和确认的真实任务回归；具体清单待冻结。后续 B 采用固定参考仓库与人工核对题集 |
| 正确性要求 | 关键检查必须通过，固定题集对必需结论的准确率不得下降；不要求准确率进一步提高，可减少可选解释以满足简洁偏好 |
| 执行环境 | 第一版本机 Docker；远程 Linux 执行后续增加 |
| 默认轮次 | 最多 3 轮，每轮 1 个候选 |
| 时间上限 | 一次优化最多 60 分钟，包含基线评测、候选生成、评测、重试和清理 |
| 提前停止 | 连续 2 轮完整评测没有改进则停止；其他预算、取消与故障条件可提前终止 |
| 用量控制 | 请求次数、单次输出上限、累计 Token 停止阈值；展示计量及未知项 |
| 实时用量 | Web 面板分别实时展示当前 Harness 会话与 RSI 分析/优化任务的 Token 消耗；分开记账，显示阶段明细、在途请求和预算状态，区分已确认与未返回用量 |
| 用户预算 | 授权时可以在宿主上限内调低预算 |
| 界面 | Harness Web 主页面右侧的 RSI 面板/卡片；设置页中的 G0 面板仅作接入验证入口 |

一次优化任务的默认范围收敛为一个受管 Skill。多个 Skill 联合优化、修改 Runtime 或控制器代码、修改评估器和权限，不属于第一版优化能力。

## 2. 第一场景：前端页面设计

用户已确认：从初始设计 Skill 出发，生成页面、接收反馈，并主动询问以确认偏好；在授权范围内迭代 Skill。轻量主动询问的频率、模型调用边界与项目内记忆规则已确认，见 [前端场景与偏好边界](FRONTEND-SCENARIO.md)。当前固定问题只在用户开始设计准备后按缺失维度提出；完整产品能力按 Gate 继续补齐。

新增确认：偏好和当前 Skill 直接送入独立模型修改任务，由模型理解偏好、提出必要澄清并生成候选文件，代码控制授权、范围、预算、检查和启用。偏好确认与本次修改授权合并在一张卡中；候选检查通过后仍另行确认启用。首次页面编写等待上述流程完成。固定六类偏好作为已有界面与历史数据继续保留，不构成新流程可理解偏好的封闭类别。详细契约见 [G2 待实现部分](G2-CONTRACTS.md#偏好驱动的独立修改任务待实现)。这些是新增产品决策，g2.2 仍只有观察纳入和一次建议分析。

首场景以可运行页面、必需内容/交互和用户明确的审美比较为证据。偏好变化与 Skill 流程改进分别记录；在新页面任务上的验证由 G3 展开。原场景 B 的题型与源码准确率示例保留为后续扩展，不直接作为前端审美评分。

### 2.1 后续场景 B：代码仓库分析

任务示例：根据问题定位实现文件与符号、解释调用链、追踪配置读取与覆盖、找出失败处理分支，并提供与冻结提交一致的源码引用。

可修改内容包括搜索策略、阅读顺序、停止搜索条件、结果组织规则，以及代码定位、片段提取和去重脚本。

该场景的主方向建议为：

| 方向 | 主要指标 | 必须一起展示的指标 |
|---|---|---|
| 定位准确率 | 固定题集正确率、关键符号/关系的命中 | 引用有效性、耗时、Token、调用数 |
| Token 效率 | 相同评测任务的完整执行 Token | 正确率、缓存情况、耗时、调用数 |
| 简洁表达 | 满足用户指定的必需信息、输出长度和解释深度 | 必需结论正确率、最终回答 Token、完整执行 Token、被省略的可选内容 |
| 完成速度 | 相同环境下完整任务耗时的重复测量 | 正确率、Token、调用数 |
| 可维护性 | 有证据的重复逻辑简化、结构改善及人工审阅 | 行为回归、静态检查、性能变化 |

可维护性不能简化为代码行数越少越好；工具调用更少也不自动等于能力提高。优化方向决定验收条件，其他指标与取舍保持可见，不制作掩盖正确性下降的总加权分。

用户可以只要求更简洁的结论，不要求原任务能力或准确率提高。例如，将仓库分析从长篇解释改为“实现位置、简短结论和必要源码引用”，在必需信息正确且完整时，可以作为偏好适配候选。可选的背景介绍、重复说明和用户没有要求的展开不必保留。

“最终回答更短”“完整执行更省 Token”“任务能力提高”是三个独立结果。最终回答更短但完整执行 Token 未减少时，可在用户选择简洁表达的前提下认定偏好已满足，报告必须注明未证实总 Token 节省；若选择的是完整执行 Token 降低，则仍需实际计量支持。不能通过减少必要核实来制造简洁，也不能把省略必需结论解释为用户偏好。

## 3. 用户流程

以下为最新确认的目标流程，尚未完整实现；g2.2 的现有操作见 README。

1. 用户提交前端需求，确认本次 Skill 是否参与迭代；同会话连续修改沿用，新会话或手动结束后再问。原有“纳入”记录仍仅授权观察，不能转换为修改授权。
2. 用户表达希望 Skill 遵循的自然语言偏好。右侧同一张卡显示偏好及作用域、必需要求、起始版本、具体可修改文件、模型路线、检查条件与总预算；用户确认后获得一次有界修改任务授权。
3. 宿主校验并冻结输入，将当前 Skill、已确认偏好和不可省略的要求发给独立模型任务。明确方向直接生成候选，无须先调用一次建议分析。模型需要澄清时按已确认上限提问；回答与后续处理沿用任务计量，不重置预算。
4. 模型修改候选副本中的授权文件，宿主封存内容、运行检查及评测。候选生成的具体规则由模型提出；模型不能修改授权、预算、检查器或日常有效版本。
5. 检查采用冻结输入。基线或候选评测不完整时，不作效果比较、不显示通过；符合要求的候选进入差异与结果审阅。单纯生成合法文件不能证明页面正确或更合意。
6. 用户另行确认精确候选；首次页面执行前绑定这个版本的 Skill 文本和资源，再开始本次页面任务。尚未执行过目标 Skill 的当前会话可首次绑定；已经使用旧版则自动创建关联新会话，带入本次需求和确认偏好，不复制旧 Skill 指令，原会话保留旧绑定。
7. 后续反馈可驱动已授权范围内的下一候选，或触发下一次优化任务；每个候选的启用仍须明确确认。原目录默认保留，写回覆盖使用独立操作。

辅助入口继续保留“本地观察 → 优化机会 → 用户确认一次分析 → 选择方向与修改授权”。用户明确提供偏好时不以观察规则命中为前提；保存偏好、分析机会或表达喜欢本身不等于提交修改授权卡。方向或范围扩大须重新确认，既有消费保留。

候选生成/检查失败、预算耗尽或用户拒绝新版时，保留旧版与已产生证据，等待用户选择“用旧版继续”或“停止本次任务”。前者使用核对后的起始版本执行页面，后者取消 RSI 及等待中的页面启动；不会自动回退、重新生成或删除已有文件。

## 4. 仓库与模块

项目继续使用当前 DeepSeek-RSI 目录作为独立仓库。现有 B1ackB/deepseek-harness fork 用于源码调试和必要的最小接入补丁，不承载日常 RSI 主体开发。

一个插件包包含宿主入口、浏览器入口与安装配置。以下是职责，不要求每项一个包或独立服务：

| 模块 | 负责 | 不拥有的决定 |
|---|---|---|
| Harness 接入 | 插件挂载、事件读取、受管技能加载、Web 通信 | 不决定候选是否更好 |
| 观察与机会分析 | 本地信号、有限证据提取、点击后模型分析 | 不修改受管 Skill、不启用版本 |
| 迭代控制器 | 授权校验、状态流转、预算、取消、串行候选调度、恢复 | 不让模型改写规则 |
| 用量账本与实时投影 | 按真实模型请求记录计量，归属任务/候选/评测，推送实时快照，提供预算读取 | 不以界面计数或模型自报代替供应商计量 |
| 候选生成 | 根据参考版本、选定目标和可见反馈修改候选副本 | 不接触批准、评分答案和有效版本指针 |
| Docker 执行 | 文件/进程操作、资源限制、产物收集、容器清理 | 不决定业务接受条件 |
| 评估 | 冻结任务、运行比较、计算结果、判定门槛 | 不直接启用候选 |
| 版本与证据 | 不可变版本、来源、差异、授权、评测、有效版本和历史 | 不根据模型自报成功改变状态 |
| Web 面板 | 机会、授权、进度、证据、启用、回退与导出覆盖 | 浏览器请求必须由宿主重新验证 |

首版不建设插件市场、远程调度平台、通用多 Agent 框架或团队权限体系。

### 4.1 基于源码研究的实施选择

建议首版采用一个 TypeScript 插件包，宿主与 Web 入口同包发布。Python/Shell 保留在被优化 Skill 及固定 Docker 评测环境中；不嵌入 EvoSkill、SkillOpt-Sleep、Memento 或另一套 Agent Loop。

- 复用 Harness：模型 provider、凭据管理、Agent 创建、Skill provider、Session 日志和现有 Web 连接。
- 插件自己负责：机会去重、持久授权、任务状态、不可变 Skill 版本、固定评估、用量归属与用户启用。
- 运行方式：用户启动 Harness 时插件随之加载；没有独立常驻 daemon、自动 nightly cron 或开机自启。用户选择并授权后才执行优化。
- 调度建议：首版全局同时执行一个 RSI 优化任务，每轮一个候选。日常会话仍可用，但速度评测遇到明显资源争用时暂停比较或标记受干扰；不把受干扰时间作为效率证据。
- 搜索方法：从最佳完整候选派生下一轮，最多 3 轮；暂不引入 GEPA/Pareto/frontier 搜索。正确任务也可因简洁或成本目标发起候选，不能限定为只有失败才优化。

建议文件职责如下，实际开发可合并小文件；这不是已创建的脚手架：

```text
src/
	index.ts          # 插件生命周期、宿主能力注册
	contracts.ts      # 授权、状态与证据结构
	store.ts          # RSI 本地事务和内容对象
	observe.ts        # 事件游标、机械信号、去重与机会
	run.ts            # 分析、串行候选、预算、取消
	evaluate.ts       # 固定题集执行、评分和接受条件
	docker.ts         # 文件/进程执行世界与清理
	usage.ts          # 请求尝试账本与分账投影
	skills.ts         # 版本封存、provider、启用与回退
	client/           # Harness 内的面板
evals/frontend/     # 待冻结的页面任务与检查；后续 B 再添加仓库题集
```

本项目脚本和代码使用 Tab 缩进。文件名与具体依赖在 G0 中确认；不因为这里列出职责就预建多包或抽象工厂。

## 5. DeepSeek Harness 接入

静态核对的底座提交为 d347e703908d0406b7a7ef80e3a0e594d86b2215；这不是兼容所有版本的承诺。实现前固定可安装版本或可复现构建，并记录依赖版本。

| 接入点 | 已有源码依据 | 需要验证的内容 |
|---|---|---|
| 外部安装 | dsh plugin、bundle 与 patch 支持外部包/本地目录 | 独立包安装、卸载、重启后加载 |
| Web 页面 | dsh.client 和 settings.plugins.tab 支持外部浏览器组件 | 构建产物格式、状态传输、按钮提交后宿主校验 |
| 技能加载 | ctx.skills 的 provider、作用域层与变更通知 | 同名优先级、会话固定版本、脚本资源路径 |
| 日常任务观察 | Session 日志、agent/*、tools/* 事件 | 增量游标、因果归属、重新加载不重复提示 |
| 工作 Agent | Agent 创建时的 setup 及作用域能力组合 | 在首次请求前锁定 Skill 和工具集合 |
| 执行边界 | fs/subprocess 是可替换的执行世界接口 | Docker 文件与进程适配、流式输出与取消 |
| 模型计量 | llm/stream、TokenUsage 和调用结果 | 重试/压缩等真实计费请求全部归属预算；请求生命周期实时推送，用量到达即更新 |
| 用户操作 | Web 域操作、现有审批与命令机制 | 跨回合授权持久化、过期批准拒绝 |

现有单次审批 ctx.approval.request 需要活动回合，不能直接作为后台优化任务跨回合持久授权的全部实现。RSI 自己保存授权对象，用现有 Web 通道承接用户操作；真正改变状态时以宿主校验结果为准。

外部浏览器包需要符合 Harness 的模块工厂格式，目前仓库内构建辅助不是已发布的外部构建预设。该兼容工作进入 G0，不预先承诺零适配成本。

G0 优先证明四条链路：外部包 → Web 操作 → 宿主持久状态；任务事件 → 受管 Skill 身份；作用域 provider → 固定版本和资源路径；真实模型尝试 → 消费归属和 usage。Docker 执行能力同时做单命令探针，不等待完整优化器写完才检查。

`llm/stream` 是单次请求流的观察位置，`llm-retry` 会记录独立的重试调度事件；不能用重试策略 ID 或 Session 步数充当全局唯一请求尝试 ID。对压缩、子调用及失败重试必须实测透传。不存在可靠消费归属的 RSI 调用不得派发；日常调用归属问题只影响记录完整性，不扩大 RSI 对日常任务的控制权。

## 6. 信任与 Docker 执行边界

建议结构：可信控制器、模型接入与评估答案留在宿主；模型驱动的任务文件操作与脚本执行进入 Docker。

Harness 工作 Agent 仍是可信运行代码，模型产生的工具调用只能进入受限执行世界。实现优先接入现有 fs/subprocess 能力，避免再造一套 Agent Loop。默认本机工具、插件自修改、任意 MCP、网络与其他宿主能力不能从工作 Agent 旁路访问。

不能只用 ctx.tools.restrict 就宣称全部隔离成立：其约束会与作用域注册和其他工具组合交互。G0/G2 必须验证实际工具清单、单调拒绝策略与每个执行入口。

Docker 模式：

| 内容 | 生成候选时 | 评估候选时 |
|---|---|---|
| 起始/参考 Skill | 只读输入 | 只读输入 |
| 候选 Skill | 独立可写副本 | 内容封存，只读 |
| 参考代码仓库 | 冻结副本，只读 | 冻结副本，只读 |
| 输出与临时区 | 独立、可写、有大小上限 | 每次执行全新可写目录 |
| 私有答案、评估器、版本数据库 | 不挂载 | 不挂载 |
| 原 Skill 目录、用户 HOME、凭据 | 不挂载 | 不挂载 |
| Docker socket | 不挂载 | 不挂载 |

容器无网络，模型调用由宿主完成，因此不用把 API Key 交给候选脚本。容器使用非 root、只读根文件系统、移除不需要的能力，并限制 CPU、内存、进程数、输出和时间。具体限额经第一组任务测量后作为宿主配置，不由候选修改。

镜像与运行依赖固定版本/摘要；安装依赖属于可信环境准备，不允许候选脚本自行联网安装。第一组仓库分析工具可使用镜像内预装的 Python、Shell、搜索工具等。新增依赖请求形成新的环境变更，不能悄悄混进效果比较。

退出时清理整个任务容器，不能仅杀死 docker exec 的宿主进程。用任务身份标识自己的容器，重启后只清理能够验证归属的资源。

容器是本项目的执行隔离边界，不提供抵御所有容器逃逸的证明。候选脚本可导致的文件、网络、资源和进程风险必须有针对性测试。

候选自带的 `test_*.py`、Shell 测试或模型新建的测试同样属于不可信执行内容，必须进 Docker。它们可以提供调试反馈，不能改写宿主冻结的关键检查、预期答案或最终接受条件。模型提出的合成题只作补充；未经用户确认不能自动进入正式题集。

封存对象仅接受授权范围内的普通文件与目录；拒绝符号链接、特殊文件和目录逃逸，限制文件总量、单文件大小及展开后大小。版本摘要包含相对路径、文件内容和执行位，不能只哈希 SKILL.md 而遗漏脚本。生成结束后先终止写入者，再封存并重新校验；评测挂载封存对象为只读。

## 7. 受管 Skill 和原文件

建议以“原始来源 + 受管副本 + 不可变版本”组织。

- 原文件保持不变，导入时记录规范路径、所有权范围、内容摘要和文件清单。
- 用户选择受管 Skill 的工作区范围；首版按工作区生效，避免一次实验改变其他项目的技能。
- 候选封存时生成内容摘要；版本号只是显示信息，授权、评测与启用都绑定摘要。
- 同一个受管范围只允许一个有效版本。同名原 Skill 的遮蔽/替换必须可确定，不能依赖偶然加载顺序。
- 同一会话绑定固定 Skill 版本及资源路径；同一会话反复读取不能混用两个版本。
- 默认启用只切换受管有效版本，新会话及尚未绑定目标 Skill 的当前会话在首次使用时取得新版；已绑定会话保留旧版。前端任务开始时可等待候选审阅后再首次绑定，不能在等待前先把旧版交给页面模型。恢复旧会话也应恢复其原绑定，版本缺失时明确报错。
- 首版每个受管 Skill 同时只进行一个优化任务或启用/覆盖变更，以宿主持久互斥防止并发冲突。

原目录覆盖是独立操作，建议命名为“将此版本写回原 Skill”。确认卡明确显示目标路径、版本摘要和完整差异。

覆盖前重新检查原目录摘要是否等于用户审阅时的值；有外部改动就拒绝覆盖并要求重新审阅。保留原目录备份和操作日志。多文件替换存在崩溃窗口，需设计暂存目录与恢复步骤，并验证原文件使用者是否还在运行；不宣称跨所有文件系统天然原子。

原目录覆盖仅在恢复测试通过后开放按钮；受管版本启用不依赖该按钮。

## 8. 数据对象与持久化

使用本地事务数据库保存元数据与状态，文件保存不可变版本和证据。本次源码确认 Harness 的 `storage-domain` 是串行的单记录 KV 写入，没有跨表事务；底层采用 SQLite 并不使上层多次写入自动成为一个事务。因此建议 RSI 使用插件拥有的一个本地 SQLite 数据库，优先采用宿主已经使用的 `node:sqlite`，不引入服务端数据库或消息队列，也不直接操作 Harness 私有表。

数据位置建议为 `<DSH_HOME>/rsi/`：`state.sqlite`、`objects/<内容摘要>/`、`runs/<任务ID>/`、`exports/<操作ID>/`。它位于用户配置目录，不写进源码仓库；版本对象和私有评分资料不得作为一个整体挂入候选容器。

| 对象 | 核心内容 |
|---|---|
| ManagedSkill | 来源路径、来源摘要、工作区范围、当前有效版本、观察开关 |
| Opportunity | 来源 Session/事件位置、技能版本、规则信号、去重标识、处理状态 |
| Analysis | 用户触发记录、读取证据范围、模型路线、建议方向与实际用量 |
| Authorization | 用户动作、起始版本、文件范围、方向、必需信息与可省略内容、偏好验收条件、评测契约、预算、撤销状态 |
| OptimizationRun | 授权、当前参考候选、轮次、截止时间、调用账本、状态与停止原因 |
| UsageRecord | 宿主请求尝试标识、供应商请求标识（若有）、消费归属（日常会话或 RSI）、关联 Session、所属分析/优化/轮次/评测、模型、开始结束时间、计量字段、计量完整性、修订序号 |
| SkillVersion | 内容摘要、父版本、文件清单、候选来源、封存状态 |
| Evaluation | 被测版本、仓库提交、镜像、题集、模型与推理设置、逐次结果、聚合指标、偏好满足情况、接受理由 |
| Activation | 审批证据、目标候选、评估摘要、预期旧有效版本、结果 |

语义状态以宿主数据库为准；模型输出与浏览器显示是候选信息或投影。文件对象先完整写入并校验，再提交数据库引用；崩溃留下的无引用对象可以清理，绝不把半写文件视为有效版本。

操作使用幂等标识与预期状态/版本检查。重复点击、过期网页、重复回调不能重复启用或覆盖新的外部改动。

以下改变需要本地数据库事务，而不是若干独立 JSON 文件写入：

- 授权状态与任务起始记录一起提交；范围、目标或题集改变后旧授权不可继续使用。
- 派发前登记唯一请求尝试并占用请求额度；收到 usage 后修订同一记录及预算投影。
- 启用时一起检查授权/评估摘要/预期旧 ACTIVE，写入启用记录并切换指针。
- 恢复时保留既有消耗，将未结算请求标记为未知，不能通过重建任务清空预算。

进程内串行不代替持久状态校验。首版一个 DSH_HOME 只允许一个拥有 RSI 写权限的宿主实例；第二实例拒绝接管运行任务，重启后的资源归属与恢复经过显式核对。SQLite 事务不覆盖文件系统和 Docker，二者使用“先完成并校验对象，再提交引用”与可恢复清理记录衔接。

## 9. 两条状态流

### 9.1 优化任务

OBSERVED → ANALYSIS_REQUESTED → PROPOSED → AUTHORIZED → BASELINING → ITERATING → REVIEW_READY → COMPLETED

任一运行阶段可转入 CANCELLED、BUDGET_STOPPED、FAILED 或 INTERRUPTED。存在完整合格候选时可在停止后提供审阅入口；不完整候选只展示诊断，不能启用。

无完整基线、基础设施错误使基线无法评定，或剩余预算不足时，不启动候选效果比较。基线 Agent 答错或未完成题目是有效的低分结果，可以成为改进起点；候选仍必须通过关键正确性检查，不能因基线有错而放松门槛。

### 9.2 单个候选

DRAFT → SEALED → VALIDATING → EVALUATING → SEARCH_ACCEPTED / REJECTED / INVALID

SEARCH_ACCEPTED 仅表示候选符合本次搜索契约，接受理由区分“指标改善”和“偏好满足”，不统一描述为能力提高。可以采用它作为下一轮参考；若用户偏好已经满足，则提前结束搜索。最终候选还需通过固定回归/保留题检查，进入 READY_FOR_USER，再经明确用户批准才成为 ACTIVE。

ACTIVE 始终与搜索参考分离。候选修改失败不影响日常有效版本；下一候选从最佳完整参考版本派生，附带允许公开的失败证据。

批准绑定候选摘要、评测契约与报告摘要、预期旧 ACTIVE 及授权状态。任一关键字段变化，旧批准失效。

搜索器输出的 `accepted`、模型自评、候选测试的 passed，都不直接触发 ACTIVE。只有宿主验证后的 Web 启用操作可以改变 ACTIVE；模型工作 Agent 不注册启用、覆盖原目录、修改授权、修改预算或修改评分器的工具。

## 10. 评估契约与场景适配

当前首场景为前端设计。固定页面需求、内容/交互检查、同任务与同偏好快照比较、用户反馈及新页面回归的边界见 FRONTEND-SCENARIO.md §3；详细题集和阈值尚未冻结。下述 B 的仓库题集与符号/引用检查作为后续场景保留；预算、版本固定、完整计量与禁止候选修改判定规则的原则继续共用。

### 10.1 后续场景 B 的数据集建议

场景 B 启动时建议采用小型、可冻结、可人工核对的 TypeScript/Python 参考仓库。可以先使用自有受控仓库，之后增加真实开源仓库，避免一开始依赖庞大业务环境。

题目覆盖：函数/命令入口定位、调用关系、配置优先级、异常处理、测试位置，以及“仓库中没有该实现”的负例。每题记录正确文件/符号、必需关系、可接受替代答案和关键误判，并将必需信息与可选解释分开。简洁表达不因省略可选解释而失分；用户明确要求解释调用链的题目仍必须包含该关系。

真实任务只有在用户确认预期答案并冻结仓库版本后，才能加入回归集。日常历史任务完成、模型自评成功和用户未反对，都不能直接当作标签。

开发反馈题与保留题在优化前划分并冻结。优化器不获得保留题答案；最终检查失败时，本次任务不根据私有答案继续修改到通过，以免消耗保留题的验证作用。

题集规模、重复次数、主指标最小改善阈值或偏好满足条件，在第一组基线测量后、候选生成前写入评估契约；不根据当前候选成绩临时调整。用户选择简洁表达时，双方版本都按同一套必需信息与表达要求比较，不能看到候选遗漏后才把必需项改为可选项。它们是实验配置，不是已证明有效的数字。

### 10.2 固定条件

固定 Harness 构建、模型 provider/型号/推理配置、Skill 摘要、仓库提交、题集版本、工具清单、容器镜像与资源限制。每次使用新 Session 和干净输出目录。

比较完整的 Agent 任务执行，不能用单独脚本微基准代替端到端改进。脚本微基准可作补充证据。

当前版本与候选使用相同任务和相同重复次数。交替或平衡运行顺序；记录缓存与环境情况。首版默认避免竞争资源的并行性能测量，以降低耗时对比干扰。

### 10.3 检查与接受

1. 结构与范围：只改授权文件；引用和脚本入口有效；依赖未越界。
2. 可运行性：Skill 可加载，脚本可启动，取消/超时可收敛，产物可读取。
3. 关键正确性：引用真实存在，关键实现/关系满足要求，无禁止副作用。
4. 固定题集准确率：必需结论的准确率不得低于对照，不要求进一步提高；所有要求的用例与重复运行必须完整。解释详略单独评价，不混入事实准确率。
5. 用户目标：按冻结契约判断指标改善或偏好满足。简洁表达允许任务能力不变，以必需信息、输出长度和解释深度验收；Token 效率要求完整执行计量支持。可维护性有静态证据与用户审阅依据，不用模型自评代替。
6. 最终回归/保留题：在进入启用审阅前通过，结果绑定候选内容。

精确的文件、符号、引用和结构性关系优先用确定性检查；需要语义判断时，明确展示模型裁判身份、版本和不确定性。宿主计算准确率和聚合指标，不信任模型或候选自己写的总分。

搜索阶段逐轮与最佳参考比较，最终报告也始终对照起始 ACTIVE。固定题集不下降只是这组测试的证据，不能表述为所有仓库上的能力保证。提升未超过测量噪声或证据不足时，显示“未证实指标改善”；若候选已满足用户授权的简洁偏好，可同时标明“偏好已满足”，进入用户审阅，不要求能力分数提高。

记录失败与拒绝的候选，避免只展示成功结果。报告同时区分“修改假设是否得到支持”和“指标是否变化”，不把偶然增益当成因果证明。

目标 Agent 给出错误答案、遗漏文件或生成无效产物，属于有效的低分评测，不以“评测无效”为由重复执行到成功。只有运行环境、评分输入或结果归属缺失等使评分无法成立的问题，才归为基础设施失败；相关重试仍消耗预算。

### 10.4 后续场景 B 的实验示例

该场景的受管 Skill 建议为“仓库实现定位与简洁解释”：定位入口、调用链、配置来源与异常分支，输出文件/符号/必要关系和简短结论。候选可优化其 Python 片段提取、去重脚本及 Shell 搜索流程。这个名称是后续工作描述，不预先创建或假定用户已有该 Skill。

先用体量小的受控参考仓库验证评分，再选本机已经有的 DeepSeek Harness 冻结提交作为真实结构样本；不扫描其他项目或个人文件。可先人工核对以下题目类型：

| 题型 | 示例问题 | 必需答案 | 可省略内容 |
|---|---|---|---|
| 入口定位 | 外部插件在哪里挂载？ | 入口文件、关键符号和调用关系 | 完整插件生态介绍 |
| 配置优先级 | 环境密钥与本地凭据谁优先？ | 读取路径、优先级和源码引用 | 安装过程回顾 |
| 数据契约 | 缓存 Token 是否计入 inputTokens？ | 字段关系、转换实现和引用 | 所有 provider 的背景 |
| 异常分支 | 请求失败后哪里决定是否重试？ | 触发事件、判定分支和停止条件 | 不相关错误类型全集 |
| 负例 | 当前存储 API 是否支持跨表事务？ | 明确否定及契约依据 | 另一个数据库方案的长篇介绍 |
| 资源解析 | Skill 的相对脚本路径怎样解析？ | 实际 provider/资源路径链 | 与问题无关的 Skill 创建教程 |

这张表只是待标注任务，不是答案已认证的题集；正式答案应独立保存并核对冻结提交。优化者不得修改任务、标签或把失败题从分母删掉。

G2 的管线演示可以使用很小的题集；G3 的效果比较另行冻结更充分的题集与重复次数。举例：开发反馈 6 题、最终保留 3 题，每题重复 2 次，最多 3 个候选，完整上限为 `6×2×(1+3) + 3×2×2 = 60` 次 Agent 任务执行；最后一项包含起始版本和最佳候选的保留题运行。一次 Agent 任务往往包含多个模型请求，不能把 60 次执行写成 60 次 API 请求。该数字只是容量示例，不是建议直接执行的成本承诺。

实际预算估算使用同一宿主预检测得的每题请求数、输入/输出、缓存、时长，再加分析、生成、裁判与失败余量。若 60 分钟和授权额度不足，应在生成候选前缩小明确的实验范围；不足以支持效果结论时，交付管线验证结果，不能宣称提升。

### 10.5 接受条件的具体例子

以下是设计示例，数值不是实测：

| 用户目标 | 候选结果 | 判定 |
|---|---|---|
| 简洁表达 | 必需结论准确率持平，回答从 800 字变为 180 字，满足约定长度；完整 Token 未下降 | 可以进入审阅，标为“简洁偏好满足”，不能标为总 Token 节省 |
| 完整 Token 降低 | 准确率持平，完整执行用量下降且超过预先规定的噪声/阈值 | 可以进入审阅，展示输入、缓存、输出和全部调用 |
| 任意目标 | 正确率下降，但混合总分因更短而上升 | 拒绝；软目标不能抵消正确性门槛 |
| 可维护性 | 重复逻辑减少，固定行为回归通过，性能无证据变化 | 展示结构差异供审阅，不宣称能力或速度提高 |
| 任意目标 | 没有完整基线、缺 usage 或关键引用无法评分 | 证据不足；不认证改善，不自动启用 |

不接受仅“分数相等且文件有变动”的无目标候选；它还必须满足用户事先选择的优化方向或偏好条件。

## 11. 预算、重试与取消

用户点击分析使用单独的小额分析预算，修改授权不由此产生。优化授权绑定最多 3 轮、60 分钟及宿主模型用量配置。

- 候选轮次：最多 3 个正式候选；生成失败不能借口“未形成完整评测”无限生成。
- 无改进计数：按用户选定的目标判断，只有完整有效评测既没有目标进展、也未满足偏好时才计入。准确率持平但已更简洁或更省 Token，不能仅因准确率未提高就计为失败。偏好或目标已满足时可以立即停止；若起始版本已经满足，则建议直接复用，不为了迭代而修改。
- 所有生成、模型重试、评测重跑、压缩、失败诊断与清理消耗时间；所有付费请求消耗请求预算。
- 基线、至少一次候选评估和最终检查在任务开始前做容量估算；不足则在授权前要求缩小冻结任务规模或调低实验目标，不能中途丢弃难题。
- 检查请求次数与单次输出上限；累计 Token 达到阈值后不再发起新请求。
- 使用供应商计量；未知计量不能当零。若用量无法可靠归属，暂停追加付费工作并报告未知范围。
- 当前 TokenUsage 的 inputTokens 不含缓存输入；缓存字段与总数须按底座契约处理，reasoningTokens 不能未经核实再次相加。
- 请求计数需覆盖真实重试，不能只数顶层 Agent 步数；总 Token 停止阈值不等于供应商账单硬上限。
- 网络/超时后的模型调用结果不明时，不能自动重复调用并声称没有重复成本。

用户取消后停止排队请求、撤销工作 Agent、结束所属容器并保存已有证据。停止等待不等于执行已停止，清理结果必须被确认。已在供应商执行的请求可能仍计费，应如实记录。

派发前先持久化请求尝试 ID、归属和额度占用，再发起模型调用。进程若在“登记后、实际派发前后”崩溃，无法确认是否计费的尝试保留为未知；不猜测成功、不默认重放。首版避免 RSI 请求并行，降低未结算用量造成的超额范围，但不能由此承诺供应商账单绝对不超阈值。

### 11.1 实时 Token 用量

实时展示是第一版功能，运行过程中即可查看，不等任务结束后才生成总计报告。面板有两个独立区域：当前 Harness 会话用量、RSI 分析/优化用量。当前会话显示其日常执行及可归属的子调用；RSI 显示机会分析、基线评估、候选生成、候选评估、最终检查、模型裁判、压缩与实际重试，各阶段分别展开。

所有用量来自同一套宿主账本，但每个请求尝试的消费归属互斥。Session 关联用于追溯，不作为再次累计的理由；当前会话触发 RSI 后，对应 RSI 请求仅计入 RSI 区域。重试、压缩和子调用继承由宿主确定的消费归属。无法归属的记录单列为待核实，不猜测分配，也不算作零消费。

| 面板字段 | 含义 |
|---|---|
| 已确认累计 Token | 已收到并归属的权威用量；计量不完整时注明“部分已确认” |
| 输入与输出 | 输入拆分非缓存和缓存部分；输出与可用的推理明细按 provider 契约展示，不重复相加 |
| 当前阶段/轮次 | 机会分析、基线、候选生成、候选评估或最终检查；可展开请求明细 |
| 请求状态 | 运行中、完成、失败、取消；在途数量及尚未返回计量的数量 |
| 预算 | 请求已用/上限、已确认 Token/停止阈值、剩余时间；未结算用量会影响实际余量 |
| 更新时间与连接状态 | 最新宿主序号、最后更新时间、是否断线或计量待补充 |

更新语义：宿主在请求开始、收到可用 usage、结束或中断时更新账本与投影，通过 Harness 现有 Web 通道推送；前端可以合并频繁更新。验收时，在连接正常的本机条件下，已收到的权威计量应在 1 秒内反映到面板，这属于待测试的界面时延目标，不是供应商逐 Token 计量承诺。

底座当前 DeepSeek 适配器将 usage 延后到流收尾处理，因此无法仅靠该接口获得每个流式片段的精确 Token 数。请求进行中展示已确认累计值及“请求进行中、用量待返回”；不能把未知输入/输出显示为零，也不能用字符数冒充 Token 数。如果以后提供过程估算，必须单列为“估算”，注明来源，并在收到权威计量后替换，不能累加两遍。

每个真实请求尝试只有一个权威账本记录。事件重复、前端重连、后台恢复和父子 Session 聚合都不能重复计数。若同一请求获得更新计量，按修订覆盖并重新投影，不把累计快照当增量相加；真正发生的重试则是新的尝试并独立计入。

浏览器刷新后从宿主快照与后续事件恢复，不能从零开始计数。预算执行与 Web 数字读取同一账本，浏览器关闭不影响预算控制。RSI 全部优化开销与某个 Skill 在评测中单次执行的用量分开：优化后的单次执行更省 Token，不代表本次优化过程已经收回成本。

范围已确认覆盖当前 Harness 会话与 RSI 任务；不冒充账号级全局消费。切换会话时当前会话区域随之切换，RSI 区域显示选定分析/优化任务，并明确任务身份。RSI 预算只约束 RSI 归属的调用，不扣减日常会话预算，也不因 RSI 超限而取消日常任务；日常会话已有的 Harness 预算仍由 Harness 管理。

## 12. 故障恢复

| 故障 | 预期行为 |
|---|---|
| 候选脚本报错 | 标记失败，保留日志；原 ACTIVE 不变 |
| 候选无提升 | 拒绝该候选；下一轮从最佳参考开始 |
| Docker 不可用 | 预检失败，不退回宿主直接执行 |
| 任务超时/预算耗尽 | 停止新增工作并清理；完整合格候选可供审阅 |
| 浏览器关闭 | 宿主在有效授权与截止时间内继续；重新打开恢复状态 |
| 宿主崩溃/插件卸载 | 持久化任务中断；重启核对资源与证据，不自动重放未知付费调用 |
| 原 Skill 外部变化 | 受管快照仍可追溯；导入/覆盖冲突需要重新审阅 |
| 旧网页确认启用 | 摘要或预期旧 ACTIVE 不匹配则拒绝 |
| 启用提交中断 | 数据库事务决定唯一 ACTIVE；未引用产物不得成为有效版本 |
| 原目录覆盖中断 | 根据覆盖日志与备份恢复，不做无证据的文件合并 |

首版在宿主重启后的策略是标记中断并让用户选择恢复；恢复可以利用完整结果，但重新核对原授权、预算、环境和版本。恢复任务不能重置已消耗预算。

日常任务出现疑似退步时只提示并提供回退，不因模糊信号自动切换版本。人工启用后的质量回退由用户决定。

开发与验证遵守用户的进程偏好：为测试启动的 Harness、容器和辅助进程，在验证完成、失败或取消后关闭，并核对端口与所属资源；用户明确要求保留时例外。不清理并非本任务创建的服务。这个规则针对开发验证，不改变“用户主动运行 Harness、只关闭浏览器时授权任务可继续”的产品语义。清理未确认时显示清理中/清理失败，不能提前报告任务全部完成。

## 13. Web 界面

2026-09-08 用户明确要求：正式 RSI 功能位于 Harness Web 主页面右侧，便于在日常任务中查看和操作。当前「设置 → 插件 → DeepSeek RSI」是 G0 接入验证入口，连接真实状态与用量账本，但其测试标记、探针列表和位置不代表最终产品界面。G1 已实现右侧入口、观察、分析预览、方向选择及授权草稿；当前验收状态见 G1-REPORT.md。

主页面右侧的 RSI 面板组织以下四类内容，不单独做网站：

1. 受管技能：来源、工作区、生效版本、观察状态和外部变化。
2. 优化机会：有限证据、触发规则、忽略/暂缓/分析操作；同一技能版本与同类信号去重。
3. 优化任务：方向、授权范围、预算、阶段、当前候选、实时 Token 用量卡、阶段/轮次明细、在途与未知计量、停止与取消。用量卡分别展示当前 Harness 会话和选定 RSI 任务，读取宿主实时投影，刷新后恢复。
4. 版本审阅：源码差异、逐题结果、效率比较、偏好满足情况、被省略的可选说明、失败记录、启用、回退和独立的原目录覆盖。将“能力提高”“成本降低”“表达符合偏好”分别标注。

2026-09-08 用户确认的桌面端交互：

- 没有已保存的展开偏好时，主页面右侧默认展开 RSI 面板。
- 用户可以手动收起或展开；记住该选择，后续打开时恢复。
- RSI 与 Harness 工具详情共用右侧区域，通过「RSI / 工具详情」切换，保留原有工具详情功能。

当前固定 Harness 源码中的 `details` 是已被工具详情占用的单一插槽，且空白会话不显示该栏；直接注册替换并不等于增加一个独立 RSI 栏。G1 已通过最小 Harness 补丁添加根作用域 `shell.panel`，验证了页签共存与无会话入口；原始提交本身不含此接口。G1 承接右侧入口、机会与用量展示，后续 Gate 按已实现能力逐步补齐操作，不提前展示可执行的优化或启用按钮。

第一版观察已有任务日志，不额外扫描用户整个磁盘。仅收集受管工作区相关事件，保存事件引用和必要摘要，不建立第二份无限增长的完整 Trace。用户可关闭观察或清除 RSI 派生记录。

机会分析只提交与当前技能相关且有大小限制的上下文，复用已配置的模型路线，不新增凭据收集。默认排除凭据字段；脱敏不能承诺覆盖任意文本中的所有秘密，分析范围应可见。

首版建议只启用 5 类机械信号：脚本失败、重试簇、重复读取、重复/过量工具输出、用户明确的简洁或成本要求。以工作区、Skill 摘要、规则和事件位置生成去重键；同类事件聚合成一张机会卡，并保留忽略/暂缓记录。提示数量上限与冷却窗口是可调宿主配置，先以少量真实使用数据标定，不搬用其他项目的固定阈值。凭证 AUTH、Docker 不可用等明确环境故障优先提示环境问题，不将其直接归因为 Skill 缺陷。

方向卡建议每次给出 2–3 个有证据的选择，而非固定堆满全部方向。每项显示必需保持的信息、拟改范围、预期收益、尚未证明的部分与估算开销。已知只有“回答太长”的证据时，不捏造“速度将提升”或“总 Token 将下降”。

产品方向已经有足够信息形成这份框架；这些未验证项保留为明确的验收门槛，不给出未经测量的“95% 已实现”承诺。运行模型、精确额度、镜像资源和题集清单在实现相应 Gate 前作为可审阅配置确定。
