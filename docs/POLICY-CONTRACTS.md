## Editable object

`PolicyContent` is a strict object containing `schemaVersion: 1`, `kind: repository-evidence-policy` and `instructions`. Instructions must be nonempty, valid UTF-8 text of at most 8192 bytes. NUL and `{{` / `}}` are rejected because the Harness prompt renderer interprets template variables. All unknown fields are rejected. Candidates cannot provide tools, model settings, file paths, budgets, callbacks, evaluators or the complete-system-prompt switch.

The host serializes the parsed object with compact JSON in schema order and hashes those exact bytes with SHA-256. Instructions retain their original characters and line endings. This digest is a policy identity, separate from Skill manifest hashes.

## Sealed versions and additive storage

`sealPolicyVersion(policyId, content, parentDigest)` writes canonical content beside the database at `policies/<digest>.json`. `policyId` is a host UUID; metadata contains that ID, digest, parent digest and host creation time. The first version has no parent; another version must refer to an already registered parent of the same policy. Repeating the exact identity/provenance is idempotent. A conflicting parent fails. Version sealing itself never changes the active selection; explicit selection is defined below.

The writer creates a private staging file, flushes it, makes it read-only and publishes it with a non-replacing hard link. Existing objects are verified, never overwritten. Reads reject symlinks, writable/nonregular/oversized files, invalid UTF-8/JSON, noncanonical bytes and digest changes. Every authorization, run start and request reservation rechecks the sealed object. No fallback object or Skill manifest is used. A filesystem publication and SQLite transaction are not one atomic operation: failure can leave an unreferenced content object, which is retained without spending authority; it is not silently garbage-collected. A stale staging file after process loss has no version authority either.

SQLite **6→7** originally added `policy_versions` and `policy_batches`. The generation gate additionally creates `policy_generations(id,data)` when opening a v6/v7 store. It does not add policy defaults to the existing `g1_state` JSON. The transaction validates old state, attempts, bindings, receipts and new provenance before committing; an invalid row rolls it back. Terminal historical rows retain their original serialized bytes, including whitespace. Earlier schema versions still receive their existing compatibility defaults. Normal startup recovery may change previously active work to interrupted/failed; that is retained lifecycle evidence, not a migration rewrite of terminal history.

Back up all RSI data with the host stopped before a real upgrade. No live user database was opened for these checks. Older binaries reject v7; restoring a complete stopped-host v6 backup is the downgrade path. Never lower `user_version` on a v7 database to simulate downgrade.

## Frozen batch authorization and transitions

`PolicyBatchInput` contains a UUID `id`, `policyId`, SHA-256 `runtimeDigest`, one or two ordered `{side, run}` entries and a batch budget. Run UUIDs and sides are unique. Two-side batches start with baseline; both entries must have the exact same conditions digest. Each run references an intact registered version of that policy. The fixture's single candidate run verifies the execution protocol; it is not paired quality evaluation.

The batch budget has `maxRequests` (1–16 reservations), `tokenStopThreshold` (1–200000), and `maxDurationMs` (100–60000). Per-run limits remain in the conditions below. These are offline controller authorizations; they do not represent user approval for real spending.

The host adds `revision`, `createdAt`, a fixed `deadline`, batch `status`, and aligned run progress (`runId`, `status`, nullable `startedAt`). Authorization is immutable. Reusing an ID with identical input returns the current record without changing progress, deadline or consumed budget. Reusing it with different input fails. Run IDs cannot be reused across batches or previous attempts, and batch IDs cannot collide with existing spending owners.

- Batch: `authorized → running → completed | failed | cancelled`; restart changes `authorized/running → interrupted`.
- Run: `pending → running → completed | failed | cancelled`; cancellation cancels remaining pending entries; restart changes pending/running entries to interrupted while retaining earlier terminal outcomes.
- Only one run is active; a second entry starts after the first is terminal. No automatic retry, resume or replay is enabled. A fresh batch needs a fresh explicit controller authorization and new run IDs.
- Completion requires native completed-turn evidence in the fixture controller and at least one request, with every request succeeded and usage confirmed. Failed, missing, cancelled or interrupted requests cannot produce completion. This records protocol completion, not answer quality or permission to adopt.
- Run time starts at host `startedAt`; the batch deadline never moves. Dispatch checks both windows and backward wall-clock movement. The parent actively closes its owned child at the execution deadline.

## Frozen run input

`PolicyRun` contains a host-generated UUID, the policy and its digest, plus execution conditions and their digest. The receiver reparses both objects and rejects mismatched digests before startup. Parsing detaches input objects; changing a caller's returned object cannot bypass validation at the child boundary.

| Condition | Current constraint |
|---|---|
| question | Nonempty string, at most 16000 characters |
| files | 1–32 explicit relative paths with their complete UTF-8 text; no NUL, absolute paths, traversal, colon or backslash; unique paths; at most 256 KiB per file and 1 MiB total |
| provider/model | Exactly `rsi-policy-fixture` / `offline-v1`; real routes fail validation |
| maxRequests | 1–8 actual requests per run |
| maxOutputTokens | 128–4096 per request |
| maxInputBytes | 1024–131072 over the system/messages/tools envelope |
| tokenStopThreshold | 1–100000 confirmed tokens; checked before each next request, not an absolute monetary ceiling |
| maxToolCalls | 1–16 allowed-tool dispatch attempts; failed arguments and denied paths consume their slot |
| maxToolResultBytes | 128–65536 bytes per successful tool result; excess fails without returning the data |
| maxDurationMs | 100–30000 ms for task execution; external controller closes the worker at the deadline |

Only policy bytes differ in a normal paired comparison. The parent records a runtime digest covering the pinned Harness commit, compiled worker, controller source and fixed evaluator source. Conditions digests alone must not compare different runner/tool implementations. The current fixed six-case checker tests structured facts and observed source references. These six cases/answers are withheld from the proposer; scripted responses do not establish a held-out real-model performance result or model improvement.

## Worker authority and tools

The controller creates a new temporary home, workspace and startup-only custom profile for each run. The profile has no default bundles: it explicitly loads SDK stdio, the native LLM/session/prompt/tool/Agent services, native Agent Loop and the fixture plugin. It loads no real provider, shell, filesystem provider, network tool, delegation, retry, compaction, memory or user instruction plugin.

The complete child environment is an allowlist, not a copy of the parent's environment. It supplies PATH, explicit DSH_HOME, telemetry-off settings and the owned job-file location. The fixture refuses ambient credential variable names. It does not read or copy a user's saved credentials. This proves an offline credential boundary; paid credential provisioning remains a separate future contract.

The fixed authority and policy sections are installed during profile composition before the SDK initialize handshake. The worker permits only its bound run UUID. A standalone fixture authorizes its own run; the paired path verifies the run already authorized/started by the controller. At synchronous Agent creation it reuses `restrictWorker`, installs only `rsi_search` and `rsi_read`, and retains the final monotonic dispatch guard. Each child has one policy/run, confining its global section to that process. The durable run binding is for evaluation accounting; dedicated pilot-session bindings are separate from these evaluation runs (see below).

Both tools read the already frozen text snapshot in memory. Search uses literal matching and returns bounded source lines. Read accepts only an exact manifest path and returns numbered lines. Neither tool opens an arbitrary host path, executes repository text, or evaluates a query as a regular expression or command. A malicious snapshot or policy can request another capability, but cannot grant it. This is a data-only policy boundary, not an OS sandbox for editable JavaScript.

## Accounting and execution

The worker reuses the existing SQLite store and `observeUsage` attempt observer. A standalone fixture has a private database in its temporary home; paired children sequentially open the controller database outside their separate homes. Evaluation requests are `owner: rsi`, `ownerId: batch.id`, `sessionId: run.runId`, with baseline/evaluation purpose. Generation requests have a distinct generation-task owner, `rsi-policy-generation/<id>` session and generation purpose. Policy-wide accounting combines both owners; batch accounting excludes generation. No old attempt field or ownership is rewritten.

The shared observer resolves policy registration before ordinary daily/probe ownership. Conflicting legacy owner maps, route/output settings, compression, reasoning overrides and unregistered sessions using a policy owner fail before dispatch. `store.reserve` independently enforces active binding, side/purpose, route, intact version, both cumulative budgets and deadlines. The observer durably reserves and marks in-flight before invoking the adapter. An in-flight request blocks another dispatch even if a usage chunk has already arrived.

`policyAccounting(policyId, batchId?)` returns retained attempts, confirmed token subtotal and total tokens. A total is null while any request is unsettled or usage is missing/partial/conflicting. A diagnostic numeric value is not confirmed usage. Proven `not_sent` requests consume a reservation slot but do not invent token usage. Unknown usage blocks the rest of that batch, including the other side, without blocking unrelated batches or daily sessions. New authorizations do not erase old unknown totals in policy-wide accounting.

Before calling the observer, `policyUsage` also verifies the exact persisted frozen run, fixed system prompt, exact ordered tool schemas and input-size bound. It rejects aborted signals and elapsed local run windows. The adapter independently checks the durable in-flight row before recording its dispatch.

The parent owns the total active deadline because the Harness middleware request object is immutable. It uses native SDK close: protocol shutdown followed by the native EOF/termination ladder. It never replaces the Harness process protocol or directly kills an unrelated PID. Initialization and shutdown have separate bounded timeouts.

Batch `completed` records execution/ledger completion only. In the paired path the parent records verified process exit, zero registered Agents and directory removal before finishing a run. The fixed evaluator separately requires that evidence. Cleanup failure retains the owned home and an explicit unverified-resource record; it stops the next child and cannot pass evaluation. No batch or evaluation status selects a version automatically.

Each normal run goes through native request, actual tool dispatch, tool result, continuation and final task termination. Provider usage in this gate is synthetic and explicitly labelled; it cannot establish real token savings. Provider failures retain confirmed usage; incomplete streams and forced process loss retain uncertainty. Graceful cancellation records cancelled attempts. Startup changes reserved/in-flight attempts to interrupted and preserves confirmed versus unknown usage, even when an unknown row has a diagnostic numeric total. It also interrupts unfinished batches without resetting consumed reservations or deadlines. Repeated recovery is idempotent. Trusted late usage settlement may update totals but cannot re-open an interrupted batch or change a terminal attempt outcome.

## Failure and cleanup transitions

1. Invalid content, conditions or digest fails before process creation.
2. Invalid model route, input envelope or exhausted request/token budget fails before adapter dispatch; no extra attempt is invented.
3. A denied capability/path or exhausted tool/result limit produces a tool error. No forbidden body or outside-path read executes. A later change to the presented tool schemas also blocks the next model request.
4. Unknown usage blocks the next request. A truncated stream or provider failure remains recorded, never promoted to a complete answer.
5. Cancel or deadline closes the owned runtime. No automatic retry or request replay occurs.
6. A forced crash leaves the durable attempt uncertain. Reopening that owned fixture store exercises existing interruption recovery without another adapter dispatch.
7. SDK close must settle, the worker PID must no longer exist, and the owned temporary directory must be removed. Cleanup failure retains the home and reports its location instead of claiming success. Normal shutdown additionally records zero registered Agents and zero forbidden executions.

The generation task is implemented below. The subsequent explicit review/selection/session contract is defined below; this generation step alone grants none of those actions.

## Paired child and fixed evaluation gate (2026-10-15)

Each of six fixed repository cases has one durable batch containing baseline then candidate. It does not pool the six cases into one spending authorization. Case inputs, a structured claim/citation answer format, expected facts and source ranges are fixed by `repository-evidence-v1`; its digest and case ID are part of the immutable authorization. Conditions and runtime identity are identical across both sides. A fixture-only mode may inject failure for validation; it does not change the frozen evaluator. Expected checks are not repository tool resources.

The controller is the only coordinator. SQLite connections are handed off sequentially, never shared concurrently: controller seals/authorizes/starts, closes its connection, then launches one owned native SDK child. A narrow trusted `openStore(file, batchId)` handoff opens only an existing v7 batch without startup recovery; it is not a restart/resume API. The worker verifies the exact already-running run and runtime, observes requests and closes the connection. It cannot create or finish the shared batch. Only after SDK exit and cleanup verification may the controller reconnect, retain evidence, finish that run and start the other side. Ordinary `openStore(file)` always performs interruption recovery. The model has no database or filesystem capability.

New optional batch fields retain `evaluationSpec`, immutable per-run `evidence`, and a derived `evaluation`. Progress gains optional `resource: {temporaryRoot,pid}`: the controller records the path before launch and the trusted worker records its PID before model dispatch. Paths/PIDs cannot be reassigned. Existing v7 rows lacking these fields remain unevaluated and retain their bytes. No schema reset, new table/package or generic executor is required. Evidence contains native events/final response, actual request envelopes and dispatch IDs, frozen identities and parent cleanup observations. Each record is bounded to 2 MiB and cannot be replaced by a different record for the same run. Results are computed by host code, with evaluated time, an evidence/ledger digest and per-side infrastructure/fact/citation checks. Callers cannot submit a passing score. Re-evaluation is idempotent; changed inputs reject the old result rather than silently recycling it. Generation and adoption revalidate this binding.

Infrastructure requires both independent processes, expected sessions/runtime/conditions/policy, native complete turns, real allowed tool results reaching continuation, settled successful attempts with matching pre-dispatch IDs, no denied tool effect and verified process/Agent/directory cleanup. Fixed quality checks validate structured facts, citation path/line existence, required source coverage and excerpts actually observed through tools. They allow different tool sequences. Wrong facts/citations produce `failed`; absent/partial/interrupted/unknown evidence produces `incomplete`. A short answer without tool execution cannot pass. Passing this deterministic checker is not semantic proof or a measured model improvement, and never activates a version.

Unknown usage or any infrastructure failure stops the batch before launching further work. Crash/cancellation retains partial evidence and consumed reservations; ordinary recovery marks remaining work interrupted without replay. A new authorization is required for a fresh comparison. Cleanup failure retains the owned home, leaves evaluation incomplete and reports the resource location; no subsequent child is launched. Controller-crash recovery may report an unresolved owned child instead of claiming cleanup. No existing process is stopped merely because its PID appears in historical evidence.

## Candidate generation gate (2026-10-15)

Generation and evaluation have separate authorization IDs, owners, sessions and budgets. A generation authorization binds one policy ID, intact baseline digest, requirements, generator input digest and an offline single-request budget. Only a host-provided development example is included. It contains a different repository task and a failure observation, with no fixed-case answer/check data. The generator receives no evaluation case selection, expected facts, previous evaluation output, database view, tools or inherited session history. User-provided requirements/baseline are explicit inputs; this boundary does not claim to remove secrets a user deliberately puts there.

The model returns exactly `{kind: candidate, instructions, rationale}`. It cannot supply policy IDs, parents, permissions, tools, model settings, evaluator fields or budgets. The host requires a changed valid literal policy, a normal completed stream and confirmed successful generation usage before sealing. It assigns parent and provenance itself. Malformed, out-of-scope, unchanged, partial, cancelled or unknown-usage responses retain their bounded raw response and ledger evidence without creating an eligible candidate. No automatic retry or paid route is enabled.

`policy_generations` is appended transactionally to the existing v7 database; old rows are not rewritten. Authorization fields are UUID `id`/`policyId`, exact `baselineDigest`, nonempty requirements (at most 4000 characters), host-computed `inputDigest` and budget. The budget permits only `rsi-policy-generation-fixture`/`offline-v1`, one request, 128–4096 output tokens, 1024–32768 canonical prompt/input bytes and a 100–30000 ms deadline. It is not paid authorization. Task fields retain revision, host creation/deadline, status, response (at most 64 KiB), candidate digest and error. Task states are `authorized → running → sealed | failed | cancelled`; startup changes authorized/running to interrupted. Exact authorization repetition is idempotent and never rearms a terminal task or resets its consumed request. Start checks revision; response checkpoints are append-only and survive interruption. Sealing registers version metadata with host-assigned `generationId` and parent plus the candidate pointer in one SQLite transaction, after immutable file publication. A crash may retain an unreferenced file, never an eligible candidate without its committed task. Restart does not infer success or replay a request.

The proposer uses the existing native LLM service directly, without an Agent Loop: it has one tool-free content-generation request. Its fixture creates a fresh LLM context with only the offline adapter; generation has no repository tools, memory or evaluation capability. This boundary is the actual model request view, not an OS sandbox for untrusted host plugins. The request observer verifies exact system/input/route and reserves the generation owner before dispatch. Persisted controller data and held-out answers are never serialized into that view. Partial output is checkpointed before completion. Unknown or conflicting usage prevents sealing even if the JSON is valid.

New generated-version metadata and linked batch fields are optional for older data. Existing v7 rows remain readable and unchanged; older v7 development builds with strict schemas can reject new generated rows, so binary downgrade still requires the complete stopped-host backup. No reverse migration or silent data deletion is provided.

After sealing, a separate evaluation authorization binds generation ID, policy ID, exact baseline/candidate digests, fixed case/spec/runtime and its own budget. It is accepted only for that sealed generation and its intact lineage. Generation permission does not authorize evaluation, and evaluation permission does not authorize generation. The existing full-task runner executes the already-authorized batch. Results remain attached to that batch/generation; no generation or evaluation state grants adoption.

`npm run policy:generation` exercises both explicit fixture authorizations and retains a new database/result under `.cache/policy-generation-<UUID>`. `tests/policy-generation.test.ts` checks the real native LLM request view, hidden-answer exclusion even with answers seeded in controller state, scope, two-generation lineage, separate evaluation ownership, no replay, unknown usage, cancellation, interrupted checkpoints, failed file publication and old-v7 preservation. See [generation evidence](POLICY-GENERATION-REPORT.md).

Run `npm run policy:fixture` for one native SDK run, or `npm run policy:comparison` for one paired fixed case. The latter retains a new controller database and result under a unique `.cache/policy-comparison-<UUID>`; child homes are removed after evidence is read. No existing database is reused by the command. Both commands require the documented Node runtime and use fixed responses only.

`tests/policy-comparison.test.ts` exercises all six cases through independent paired children, cumulative budgets, unknown usage on either side, child loss/reopening without replay, wrong facts/citations, correct tool-free answers, cancellation/deadline, immutable evidence, changed evaluator conditions, old-v7 compatibility and missing cleanup receipts. The existing policy and persistence tests remain. Policy generation, held-out/repeated real-model evaluation, user adoption/restore and ordinary-session bindings are next steps. None can turn the fixture route into paid authorization.

## Explicit review, selection and session binding (2026-10-15)

This increment enables sidebar review and explicit workspace defaults for the **fixed-response read-only pilot**. It does not enroll ordinary chats or add a real provider route. A new pilot session uses the selected batch's frozen source snapshot and limits; its creation does not dispatch a request. The fixture adapter must be installed separately in a test profile. There is no paid-call fallback.

- Review displays the exact baseline/candidate instructions, generation rationale, frozen question/source manifest, full-task outputs, infrastructure/quality results and ledger totals. Opening review is free. Selection requires a separate explicit user command; a score never selects a version.
- `policy_adopt` binds workspace, policy, exact version pair, batch, derived evidence/ledger digest, baseline/candidate choice, expected current **choice ID** and snapshot revision. Both complete sides, verified cleanup, intact objects and known usage are mandatory. A complete but incorrect answer remains selectable with its failed quality result visible. Generated provenance must still match. Baseline selection is an explicit approval too; an unselected baseline is not automatically approved for restoration.
- `policy_restore` targets a prior explicit approval in the same workspace, exact expected current choice ID and revision. The host rereads intact object and approval evidence. Append-only choices are the active pointer: the last committed choice for the workspace wins. Choice and the existing command receipt commit in one SQLite transaction; lost replies can be retried exactly. No filesystem ACTIVE file, rewrites of old sessions, or automatic replay are required.
- `policy_session` separately confirms the current choice and creates an immutable dedicated session binding and command receipt atomically. It freezes the chosen version and original conditions before Agent creation or prompt assembly. Repeating the operation recovers provisioning with the same session ID. Sidebar `policy_open` explicitly reopens a recorded session after interruption; restart alone never dispatches. Existing ordinary or pilot sessions are never rebound, including sessions that have not yet made their first request.
- Native creation setup installs the literal scoped prompt, fixed authority, bounded snapshot tools and final capability guard synchronously. A synchronous creation listener does the same for native UI resume before the first assembly. It records the fixed model selection before any request header, even when native permission/sandbox initialization already added events, and attaches the created session to its native workspace before returning it to the client. Resume rejects missing/corrupt bindings or objects. The global usage observer verifies the fixed route, exact tool schemas, literal policy/authority, input/output caps and independent daily owner before adapter dispatch. Session requests reuse daily accounting and fixed cumulative limits; unknown/interrupted usage prevents additional requests. The evaluation batch is immutable and is never reused as a daily spending owner.
- SQLite 7 appends `policy_choices` and `policy_sessions`; old v6/v7 terminal rows remain byte-for-byte intact. Opening validates new identities/references and rolls back on corruption. Existing Skill JSON/bindings retain their meaning. Back up the stopped host database and object directories together before upgrade; old strict v7 readers are not a supported downgrade path.

### Final review clarifications (2026-10-16)

New adoption still requires both intact version objects and complete, unchanged paired evidence. Restoration and new session binding for an existing explicit approval reread only the selected object; the other side's lost/damaged object cannot prevent recovery to an intact approved version. The original frozen pair, generation provenance/usage and evaluation evidence/ledger are still revalidated. Missing or changed selected bytes, approval references, evidence or usage fail without appending a choice or binding.

Native resume may provide only provider/model Agent options before any request header exists. The scoped request hook fills an absent output cap from the immutable binding before dispatch; an explicit conflicting cap or route is still rejected by the global guard. This applies equally to the RSI reopen command and the native session entry. Changing workspaces clears any pending sidebar confirmation so a choice for a previous workspace cannot be confirmed from the newly selected workspace's card.

## Real repository snapshot capture (2026-10-16)

The [snapshot contract](POLICY-SNAPSHOT-CONTRACTS.md) defines explicit exact-file capture from a real local checkout. `src/policy-snapshot.ts` reads bounded regular files without following links, checks for concurrent changes, rejects sensitive paths/content and seals current worktree bytes using the same immutable JSON publication as policy versions. `repositorySnapshotSchema` is the executable source of truth; a review manifest is derived. Conditions optionally include `sourceSnapshot: {root, digest}`, validated against those exact sorted files. Missing provenance on historical conditions remains valid and does not change their digests. No SQLite migration, new optimization object or adoption action is added. Old strict builds cannot read new source-bound conditions; use the complete stopped-host backup for downgrade.

The developer command's optional offline verification runs search/read/continuation in the existing independent native subprocess. It checks captured source transport, scope, accounting and cleanup, not arbitrary repository answer quality. Fixed casebook inputs/answers and existing adoption/session binding stay unchanged. No real route, credentials or paid calls are enabled. See [validation](POLICY-SNAPSHOT-REPORT.md).

The subsequent [sidebar source contract](POLICY-SNAPSHOT-CONTRACTS.md#sidebar-selection-and-dedicated-sessions) adds `policy_preview`, `policy_seal` and `policy_source_session`, one `policy_sources` table in unreleased v7, and optional source IDs on new session bindings. Preview exposes full captured bytes; confirmation recaptures and requires exact agreement. Source/workspace/policy/revision conflicts fail without authority. Session intent and receipt commit before provisioning and do not dispatch. Old bindings continue using their original batch source. This does not reevaluate or automatically adopt a policy on arbitrary source. See [source UI evidence](POLICY-SOURCE-UI-REPORT.md).
