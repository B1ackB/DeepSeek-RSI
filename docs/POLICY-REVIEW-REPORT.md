# Repository policy review and session-binding gate

Implemented and verified on 2026-10-15 with Node 25.8.1 and Harness `0.1.3-alpha.1` at `d347e703908d0406b7a7ef80e3a0e594d86b2215`. All model responses were fixed fixtures. Paid requests: **zero**.

This increment completes user review, explicit workspace selection and restoration for the existing repository-evidence-policy pilot. It reuses the RSI sidebar, `/rsi` commands, long-poll snapshots, operation receipts, version objects, native Agents and existing attempt ledger. It does not add another optimization object, dependency, scenario abstraction or automatic adoption rule.

## Implemented behavior

The sidebar displays both complete instruction texts, generation rationale, frozen question/source manifest and limits, actual source-tool results, final answers/citations, infrastructure/quality checks, request/tool counts and known/unknown tokens. A choice opens a separate confirmation; cancellation and review make no model requests. The current session's recorded choice and the default for future sessions are shown separately.

`policy_adopt` binds an exact baseline/candidate pair, policy, batch and evidence/ledger digest. The host rereads both objects, generation provenance/response/usage and paired full-task evidence before committing. Incomplete infrastructure, unknown usage, changed evidence, missing cleanup or corrupt objects block selection. Complete but incorrect answers remain selectable with their failed quality result visible: scores never select a version. Cached passing results are displayed as incomplete if current validation fails.

`policy_restore` accepts a prior explicit adoption in the same workspace. Selecting a candidate does not silently approve its baseline for future restoration. Both commands compare snapshot revision and the current choice ID, including changes away and back to the same content. Append-only `policy_choices` records are the active pointer. Choice and existing `g1_operations` receipt commit atomically. Repeating an identical command returns its original receipt; conflicting reuse fails.

`policy_session` separately freezes a selected version, batch snapshot, limits and workspace in `policy_sessions`, committing that intent and receipt before native provisioning. Creation itself makes no model request. A lost reply or workspace-attachment failure can retry the same operation without creating another session. `policy_open` explicitly reopens the recorded session after interruption; restart alone never runs it. Missing history after attempted execution fails closed.

Creation setup installs the scoped literal policy, authority and bounded snapshot tools. A synchronous native creation listener also installs them on native UI resume before first prompt assembly. Native permission initialization can already have written events, so fixed model selection is recorded before the first header regardless of an otherwise nonempty log. The session is attached to its native workspace before client navigation. Ordinary sessions do not inherit policy defaults. Already bound sessions retain their version even if their first request happens after another adoption.

The existing usage observer validates the fixed route, policy/authority, tool schemas and input/output limits before dispatch. The store independently checks identity, cumulative requests/tokens, settled usage and persisted time window. Scoped guards deny inherited and later tools; tools read the frozen snapshot only. Timers cancel overlong native work and are disposed with their Agent. Daily calls retain session/daily ownership and join policy-wide totals; evaluation batch totals exclude them. Interrupted work cannot restart its budget even after late usage settlement.

## Compatibility and limits

SQLite remains version 7 in this unreleased development path. Opening appends only `policy_choices` and `policy_sessions`; existing Skill JSON, receipts, bindings, terminal attempts and old policy rows retain their bytes. New references and exact creation receipts validate before migration commit. Invalid records roll back rather than clear history. Back up the stopped host database and object directories together. Older strict v7 readers cannot consume the new command/record shapes; downgrade uses that complete backup. Hot replacement of the plugin while external Agents remain active is not a supported upgrade path.

The entry is deliberately the **fixed-response read-only pilot**. New sessions reuse the selected batch's frozen source snapshot, fixture route and limits. The fixture adapter is installed only by test helpers; absent that adapter, requests fail without paid fallback. This is a trusted host plugin capability boundary, not an OS sandbox: native permission labels may still say workspace-write, while the scoped tool set contains only snapshot read/search. No candidate component code executes. Live repository snapshot capture, real provider credentials/budgets, paid comparisons and generation/evaluation controls in the sidebar remain separate work. These tests establish lifecycle reliability, not real-model improvement.

Reproduce core checks with `PATH="/opt/homebrew/bin:$PATH" npm run check`. `preparePolicyReviewFixture(file)` in `scripts/policy-review-fixture.ts` creates fresh generation/evaluation history. For browser verification, build with `node scripts/build.mjs --policy-review-fixture`, use a fresh `policy-review-home`, disable the real provider, load the guarded browser fixture, then run `node scripts/browser-policy-review.mjs <isolated-result-directory>`. Authenticated launch URLs/logs stay in `.cache/`; they are not published evidence. Close the owned host after the browser script finishes.
